# DECISIONS.md

**1. Indexes.** `employees.emp_code` unique; `employees.department+joined_on` and `employees.joined_on` for headcount. `attendance_logs` gets `emp_code+date` unique (punch-in's race guard, and the employee-scoped listing order), `emp_code+punch_in` (punch-out finds the latest record), `date desc+emp_code` (the default sort and every month-range analytics scan) and `status+date` (filtered listings). I rejected an index on `work_hours`: nothing queries or sorts by it, so it would only cost write time.

**2. Punch-in race.** Two identical requests arrive together. Both read the employee, compute the same `date`, build the document and call `insert_one`. The **unique index on `(emp_code, date)`** is the only arbiter: the server serialises the two inserts, one succeeds, the other gets `DuplicateKeyError`, which I turn into 409. So exactly one 201. There is no `find_one` first — a read-then-write has a window where both requests see nothing.

**3. Ties.** `$rank` inside `$setWindowFields` gives standard competition ranking: tied totals share a rank and the next one is skipped (1, 2, 2, 4). I then match `rank <= limit`, so a tie sitting exactly on the cutoff returns **both** members — `limit=3` can return 4 rows. Using the array position would number that group 3 and 4 and be wrong. Rows are ordered by total descending, then `emp_code` ascending.

**4. Headcount.** The summary starts from `attendance_logs` and uses `$unionWith` to add a second branch that groups `employees` by department. Because it is a union, a department whose only employees have no logs still produces a row: it arrives via the employees branch with zeroed counters and a real headcount. `$match` on `joined_on <= last day of month` excludes people who have not joined yet (R9). The two branches are then merged by department. Driving from logs rather than employees is deliberate — it keeps the leading `$match` on an indexed `date`, so no collection scan appears in front of every call.

**5. At 100× the data.** The department summary and leaderboard are the two that would hurt, because both group a full month. The department summary could become a daily rollup collection updated at read time, and the leaderboard a monthly summary per employee. I would add a `(date, emp_code)`-sharded collection and `$lookup` from employees to logs via `$unionWith` so the join happens in the database. For the trend, capping the range (already 92 days) keeps `$densify` bounded, which is the only part that cannot be indexed.
